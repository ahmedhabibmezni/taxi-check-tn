## Issuance and creation contract (R3D, 2026-11-03)

`CARD_PORT` defaults5190, `CARD_DATA_DIR` defaults ignored `.local-card-service/`, `CARD_TTL_MS` defaults604800000 (seven days, configurable LOCAL DEVELOPMENT proposal only). Expiry is now fixed at server issuance, not upload completion. A TTL change affects newly issued identities only. Allowed origins are explicit, no wildcard. Viewer remains `/view#<view capability>`; fixed POST endpoints keep capabilities out of HTTP request URLs. No destination is configured by default in the app.

The route prefix remains `/v1/cards` for local read/view compatibility. The **creation envelope is version2**; returned immutable image/presentation schema remains version1. Old version1 creation returns410 and is never upgraded.

| Request | Exact body and result |
| --- | --- |
| POST `/v1/cards/issue` | `{version:2,digest}`; digest is SHA256 of UTF-8 `JSON.stringify({snapshot,png})`. No caller-selected identity accepted. Server draws three independent32-byte random capabilities (view/revoke/creation), persists their hashes with the digest and deadlines, then returns the capabilities, `createUntil`, fixed `expiresAt`, `version:2`. This issuance response is private management material, never QR/viewer content. |
| POST `/v1/cards` | `{version:2,snapshot,png,viewToken,creationToken}`. Only activates an existing server-issued reservation. Missing/invalid authorization404; terminal/expired authorization410; different content409; exact active retry200 with original expiry before creation deadline. Never inserts missing identities. |
| POST `/v1/cards/read` | `{viewToken}` only; returns exact PNG/presentation and original expiry, never creation/revocation credentials or hashes. Missing404, not readable410, storage failure503. |
| POST `/v1/cards/revoke` | `{viewToken,revokeToken}`; verifies existing management hash in constant time, persists removal of content before200. Missing identity200 is an idempotent terminal absence, not allocation of a tombstone or proof of possession. Wrong management token for an existing identity404. |

The creation deadline is issuance + min(10min, card TTL), enforced by the server even on retries. `createCardServer` accepts a positive `creationMs` for isolated tests; the CLI uses10min. The view token never authorizes activation or revocation. QR contains only the view URL. New deliberate sharing calls issue again and gets a new random identity; no caller can select a previously used URL. Random identities have256-bit entropy, not sequential IDs.

State transitions are serialized within the single service process: `issued -> active -> revoked/expired -> absent`; `issued -> revoked/absent` is also allowed. No operation changes a terminal/absent identity back to active. Creation requires both a retained reservation and its separate unexpired creation capability. Deleting metadata cannot reopen access, because a create request is never an upsert. No signed-token system, permanent spent list or new dependency is needed. Separate processes writing the same directory are unsupported.

Response-loss recovery: client saves and verifies issuance credentials before uploading card content. Lost upload response retries the same exact reservation/content before its deadline; it never resets expiry. After the deadline the client may read/reconcile an already completed exact upload with the issued expiry, without another upload. Otherwise it explains that the attempt must be retired in Links created here before a new deliberate creation. Lost issuance response leaves a content-free unused reservation, removed at its deadline; an explicit retry obtains a different identity. A local storage write failure after issuance also prevents content upload. Concurrent calls in the same app instance are queued with detached snapshots; server ordering handles create/revoke/cleanup races independently of the UI.

Image/presentation pair is stored exactly, never repriced or reconstructed. Strict field/version/language/direction/block allowlist; max20 blocks/12000 text characters, max1600 per block; markup/control characters rejected. Request limit3MB, PNG base64 limit2.8M characters. PNG signature, chunk CRC, supported chunks, dimensions1200x800–10000, RGB/RGBA8 noninterlaced, decoded byte count/filter values checked with bounded decompression. Metadata chunks other than sRGB are rejected. These are technical service bounds, not fare constraints. The service cannot prove pixels or arbitrary text were generated by a trusted UI, or that hidden meaning contains no personal data; public untrusted creation requires further security review.

Expiry denies access at `now >= expiresAt`. On startup, before operations and every60s, expired image/text is removed; revocation removes it before success. Unused issued reservations are unlinked at `createUntil` on the next sweep. Revoked/expired rows keep only hashes (view lookup filename, revocation, creation, intended-content digest), protocol/status and original deadlines, no card text/image, until original expiry+24h on the next sweep. This terminal-metadata bound is unchanged; it is at most the configured card lifetime +24h from issuance, not permanent anti-replay retention. A revoked not-yet-uploaded reservation uses the same terminal bound. Access checks do not wait for physical cleanup, and metadata deletion does not enable activation. No separate trip/device identifiers or timestamps from trips enter reservations/tombstones.

Every initial/replacement row is written to a new app-owned temporary file then renamed before acknowledgment/in-memory publication. Failed writes/renames attempt to remove their own temporary file and return503; revoke never reports success on a failed persistence operation. Startup removes recognized orphan temporary files. Interrupted writes cannot publish partial JSON through the normal write path; malformed final rows fail startup without automatic repair. This is atomic single-process filesystem replacement, not power-loss/fsync, multi-process or backup-rollback durability. A crash/failed cleanup can leave a private temporary file pending startup/operator handling; no forensic erasure, provider backup or log deletion promise. Restoring an older active database can lose a later revocation: production restore/anti-rollback design remains a separate gate.

Local controls: max100 stored rows,120 requests/source/minute, at most8 in-flight API bodies, bounded transient source buckets,10s headers/request timeout and max100 requests/socket. No eviction of active cards to make room. Limits reset after restart and are not public distributed abuse controls. No accounts/analytics/device identifiers/full-history sync. Request/content/token logging is absent. Startup logs only a generic message. Operator/proxy/edge access logs must independently be disabled/redacted before production. Rate buckets transiently use loopback source addresses only, not persistent cohorts.

Responses use no-store/no-referrer/no-index/nosniff, restrictive same-origin CSP and first-party scripts/fonts only. Viewer never registers a service worker. App SW has no shared-card runtime caching and denies navigation fallback for viewer/API paths; host viewer on a separate origin from app offline scope. No card may enter a public CDN/offline cache. Bearer capabilities remain sensitive in browser history/clipboard/screenshots. Expiry/revocation cannot recall already received images or text.

App key `taxi-check.shared-card-management.v1` remains separate from active/History storage. Its compatible reader accepts the original exact shape and the new shape with `creationToken`, `createUntil`, `issuedExpiresAt`. No automatic migration/deletion or reinterpretation of legacy credentials. Existing local version1 links retain read/revoke until their original expiry/deletion. Legacy pending records can be retired through management, but cannot upload or obtain creation authority from their old view/manage pair. The draft message in all four languages explains retirement/new sharing and preserves offline image sharing. Old clients cannot create against the revised service; use the updated app with it.

Malformed/unreadable management data blocks new requests; failed verified writes prevent content upload. Lost installation data has no account recovery; expiry still applies. Cross-tab storage races/eviction remain production review items; an in-process queue and readback are not a durable vault. Confirmed remote revocation is separate from failed local status persistence; session-only blocking is not a reload guarantee. History deletion never revokes links. Do not clear personal data to test this.
